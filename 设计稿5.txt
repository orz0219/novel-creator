有。我重新从**后端工程实现**的角度把我们前面的设计过了一遍。结论是：

> **领域模型方向没有明显错误，但后端还缺少一层“运行时基础设施”。**
>
> 前面我们设计得比较多的是「数据是什么」，现在需要补上「这些数据怎么安全、可靠、可恢复地运行」。

尤其你现在明确使用 **DuckDB + Rust**，这一点会影响几个关键设计。DuckDB 当前官方文档明确强调：它非常适合**单进程内的并发读写**，但多进程写同一个数据库文件并不是主要设计目标；同一进程内可以通过多个连接/线程并发，但发生写冲突时会出现事务冲突。([DuckDB][1])

所以我建议你把后端重新整理成下面这个结构。

---

# 一、我认为目前真正缺少的是这一层

之前我们大概是：

```text
Domain
    ↓
Application
    ↓
Context Engine
    ↓
Skill Runtime
    ↓
LLM
```

我现在建议改成：

```text
                    API / UI
                       │
                       ▼
              ┌─────────────────┐
              │ Application API │
              └────────┬────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
     Commands        Queries       Jobs
        │              │              │
        └──────────────┼──────────────┘
                       ▼
               ┌───────────────┐
               │ Domain Layer  │
               └───────┬───────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       World       Narrative     Knowledge
          │            │            │
          └────────────┼────────────┘
                       ▼
               Repository Layer
                       │
                       ▼
                  DuckDB
```

旁边再挂：

```text
LLM Runtime
Context Engine
Skill Engine
Validator
Event/Job System
Artifact Storage
Observability
```

也就是说：

> **LLM 不应该直接碰数据库。**

# 二、第一处需要修正：不要把“Event Sourcing”做得太彻底

前面我说：

```text
Event
 ↓
StateChange
 ↓
Projection
```

这个思想是对的。

但我不建议 V1 做成严格意义上的完整 Event Sourcing。

也就是说，不要搞成：

> 所有东西都只能通过 replay 计算出来。

那会把系统复杂度提高很多。

---

## 建议采用：

### Canonical Data

```text
entities
facts
relations
current_states
characters
locations
...
```

### Immutable History

```text
events
state_changes
knowledge_changes
relation_changes
```

### Projection

```text
current_state
current_knowledge
current_relations
```

也就是：

```text
历史记录
+
当前快照
```

两套都保存。

---

# 三、为什么这么做？

假设第 1000 章：

```text
林凡
境界 = 元婴
```

你当然不希望每次查询都：

```text
从第一章开始 replay
→ 计算 999 次变化
→ 得到元婴
```

所以直接保存：

```text
character_state
cultivation = 元婴
```

同时历史里保存：

```text
StateChange #1281
炼气 → 筑基

StateChange #2932
筑基 → 金丹

StateChange #4811
金丹 → 元婴
```

这样：

```text
正常运行 → 查 Projection

审计 / 回滚 / 重建 → 查 History
```

这才比较适合你的项目。

# 四、第二处必须补：Repository 不能直接等于 SQL

我建议明确分三层：

```text
Domain Repository Interface
        ↓
Application Service
        ↓
DuckDB Repository Implementation
```

例如：

```rust
trait CharacterRepository {
    fn get(id: EntityId) -> Result<Character>;
    fn save(character: Character) -> Result<()>;
}
```

Domain 不知道：

```text
DuckDB
SQL
Connection
Transaction
```

然后：

```text
DuckDbCharacterRepository
```

负责真正 SQL。

# 五、第三处：必须有 Unit of Work / Transaction Boundary

这个我认为是前面设计中比较大的遗漏。

例如一次 Scene Commit：

```text
Scene 完成
 ↓
创建 Event
 ↓
创建 StateChange
 ↓
修改 Character State
 ↓
修改 Knowledge
 ↓
修改 Relation
 ↓
更新 Ledger
 ↓
更新 Scene Status
```

这些必须：

> **要么全部成功，要么全部失败。**

所以应该存在：

```rust
UnitOfWork
```

概念：

```text
BEGIN

insert event
insert state_changes
update character_state
insert knowledge_change
update relation
insert ledger
update scene

COMMIT
```

失败：

```text
ROLLBACK
```

DuckDB 本身支持事务、快照隔离和回滚，所以这个边界完全可以利用数据库事务实现。([DuckDB][2])

---

# 六、第四处：必须设计“写入队列”

这和你选择 DuckDB 有直接关系。

你的系统以后很可能同时运行：

```text
Scene Writer
Character Agent
Validator
Knowledge Extractor
State Extractor
```

如果这些 Agent 都自己拿 DuckDB Connection 去写：

```text
A → UPDATE
B → UPDATE
C → INSERT
D → UPDATE
```

你很容易遇到 transaction conflict。

DuckDB 在**单进程内部**支持并发 writer，但冲突写同一行时会失败；官方也明确建议针对这种冲突进行重试。([DuckDB][1])

---

## 所以我建议：

```text
                    Agents
                       │
                       ▼
                Command Bus
                       │
                       ▼
                 Write Queue
                       │
                       ▼
               Transaction Worker
                       │
                       ▼
                    DuckDB
```

注意：

**不是所有数据库操作都必须排队。**

读取：

```text
SELECT
```

可以并发。

真正的：

```text
State Commit
Canon Commit
Project Mutation
```

进入统一写入协调层。

---

# 七、第五处：增加 Command / Query 分离

我非常推荐你采用轻量 CQRS 思想。

不是搞复杂 CQRS。

简单分：

### Query

```text
GetCharacter
GetLocation
GetContext
GetTimeline
SearchEntities
```

只读。

### Command

```text
CreateCharacter
ApproveLocation
CommitScene
ApplyStateChange
RejectProposal
RollbackScene
```

会修改数据。

于是 API 很清楚：

```text
GET  → Query
POST → Command
```

# 八、第六处：所有 AI 修改必须走 Proposal

这是我认为你后端最核心的安全边界。

例如 AI 输出：

  "new_value": "location_yyy"

**不能直接执行。**

后端转换成：

```text

```

然后：

```text

 ↓
Schema Validation
 ↓
Domain Validation
 ↓
Canon Validation
 ↓
Conflict Detection
 ↓
Approval
 ↓
Commit
```

# 九、Proposal 还应该有状态机

```text

 ↓

 ↓
VALID
 ↓

 ↓
COMMITTED
```

异常：

```text

```

这样以后你在 UI 里可以直接看到：

> AI 刚才想修改了什么。

# 十、第七处：增加 Optimistic Version

例如：

```text
Character
version = 12
```

Agent A 读取：

```text
version = 12
```

Agent B 也读取：

```text
version = 12
```

A 修改成功：

```text
version = 13
```

B 再提交：

```text
UPDATE character
SET ...
WHERE id = ?
AND version = 12
```

发现：

```text
affected_rows = 0
```

说明：

> 这个对象已经被别人修改。

于是：

```text
CONFLICT
```

而不是覆盖 A 的修改。

这层最好在应用层也做，即使数据库本身有并发控制。

# 十四、第十处：Generation 不要和 Job 混在一起

所以应该分开。

# 二十九、第二十五处：事务不能跨越 LLM 调用

这个必须明确写进架构规范。

绝对不要：

```text

 ↓
调用 LLM
 ↓
等待 30 秒
 ↓
LLM 返回
 ↓
COMMIT
```

这是错误设计。

应该：

```text

 ↓

 ↓
得到 Proposal

重新读取当前状态
 ↓
Validate
 ↓
短事务
 ↓
Commit
```

也就是说：

> **LLM 是外部不确定操作，数据库事务必须短。**

# 三十、这一点和 DuckDB 特别相关

因为 DuckDB 本身更偏分析型数据库，并不是为大量“小事务 + 高并发 OLTP”而设计的。官方也明确指出，大量小事务并不是它的主要优化目标。([DuckDB][3])

所以你的架构应该：

```text
LLM
    ↓
大块处理
    ↓
一次 Proposal
    ↓
短事务 Commit
```

而不是：

```text
AI 每生成一句话
 ↓
UPDATE
 ↓
UPDATE
 ↓
UPDATE
```

# 三十二、如果使用你现在的 Rust + DuckDB

我会建议技术边界大致这样：

```text
Axum
  ↓
Application Service
  ↓
Domain
  ↓
Repository Trait
  ↓
DuckDB
```

异步：

```text
Tokio
```

序列化：

```text
Serde
```

实时：

```text
WebSocket
```

但有一个非常重要的点：

> **不要把 DuckDB 当成 Tokio Async Database。**

数据库查询本身是同步计算/IO 模型，应该通过合适的阻塞任务边界处理，而不是把大量 DuckDB 操作直接塞进 async executor 的核心路径。

# 三十三、我现在会给 DuckDB 加一个明确的定位

不要把它定义成：

> “整个系统的万能数据库。”

而是：

> **Novel Engine 的本地 Canon / State / Analytics Store。**

它非常适合你的 V1：

```text
单用户
单应用
本地运行
大量结构化数据
复杂分析查询
Context Retrieval
Timeline 查询
Graph-like Relation 查询
```

这其实非常契合 DuckDB。

但后端必须保证：

```text
所有写入
      ↓
同一个 Rust 进程
      ↓
统一 Database Service
```

而不是让多个 Agent / Worker 进程各自打开 `.duckdb` 文件。DuckDB 官方目前仍明确说明：多进程对同一个原生数据库文件进行写入并非默认支持的主要使用模式。([DuckDB][1])

# 三十六、我认为现在后端最大的“错误风险”其实只有三个

### ① 把 DuckDB 当传统高并发业务数据库

**不要。**

你的应用应该是：

```text
Rust 单进程
    ↓
多个 async tasks
    ↓
协调 DuckDB
```

而不是：

```text
多个 Agent 进程
    ↓
共享 DuckDB 文件
```

DuckDB 单进程内的并发能力是可以利用的，但写冲突仍需要处理。([DuckDB][1])

---

### ② 让 AI 直接修改世界

**绝对不要。**

永远：

```text
LLM
 ↓
Proposal
 ↓
Validator
 ↓
Commit
```

---

### ③ 把正文当成世界数据库

**也不要。**

应该：

```text
World Model
    ↓
Narrative Plan
    ↓
Draft
```

而不是：

```text
Draft
 ↓
猜测世界
 ↓
更新数据库
```

---

# 三十七、所以我现在认为你的后端已经可以“冻结”了

如果让我给这个 V1 架构下一个最终判断：

**没有必要再继续增加核心数据库概念。**

现在应该从：

> “还缺什么？”

转向：

> **“把这些东西的边界精确下来。”**

尤其下一步应该真正开始写：

**逐表精确到字段、类型、索引、约束和关系。**

这两份东西一旦定下来，你再交给 CodeAgent，就不会出现我们前面最担心的情况：

> Agent 写着写着发现一个概念没有定义，于是自己发明一套；另一个 Agent 又发明另一套，最后整个后端逐渐失控。

而且以你现在的 **Rust + DuckDB** 方案来说，我认为 **V1 完全可以继续用 DuckDB，不需要为了“看起来专业”就提前换 PostgreSQL**。真正需要解决的是把**单进程写入协调、短事务、Proposal/Commit、Job 生命周期和不可变历史**这些边界做好。([DuckDB][1])
