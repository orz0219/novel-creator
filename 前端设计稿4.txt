# Novel Engine

## Architecture & Development Specification

> 版本：V1.0
> 定位：小说创作 IDE / Story Engine Client
> 核心理念：**让小说世界成为一个可持续运行、可验证、可追踪、可演化的系统。**

---

# 1. 产品定位

Novel Engine 不是传统的小说管理后台，也不是简单的 AI Chat + 小说编辑器。

它是一个：

> **World State + Story State + Context Engine + AI Generation + Validation + Versioning**

组成的小说创作工作台。

用户面对的不是一个聊天机器人，而是一个：

> **正在运行的小说世界。**

核心工作流：

```text
World
  ↓
Story
  ↓
Context
  ↓
Generation
  ↓
Proposal
  ↓
Validation
  ↓
Command
  ↓
Commit
  ↓
Event
  ↓
Version
```

---

后端定位：

> Domain Logic、业务规则、Context、Validation、Generation Orchestration、Persistence。

```text
DuckDB
```

前端不得直接依赖数据库表结构。

```text

openedPanels

activeTab
```

Workspace State 不得污染 Domain State。

# 7. Entity

所有具有独立身份、可以被引用的对象统一抽象为 Entity。

例如：

```text
Character
Location
Faction
Item
Event
Story
Chapter
Scene
Thread
Foreshadow
```

每个 Entity 必须具有稳定 ID。

推荐：

```text
entity_id
entity_type
created_at
updated_at
version
```

Entity ID 一旦创建，不允许因为名称变化而改变。

---

# 8. State

State 表示 Entity 在某个时间点的状态。

例如 Character：

```text
alive
location
health
age
emotion
inventory
relationships
```

重要原则：

> 不要把所有状态都简单存成静态字段。

可以由：

```text
Canonical State
+
Timeline
+
Events
```

推导：

```text
Derived State
```

---

# 9. Canonical State 与 Derived State

## Canonical State

真正需要持久化的事实：

```text
出生日期
死亡事件
移动事件
关系变化
获得物品事件
```

## Derived State

根据事实计算：

```text
当前年龄
当前地点
当前持有物
当前状态
```

尽量避免重复存储 Derived State。

目标：

> **减少世界状态不一致。**

---

# 10. Relationship

Relationship 是一等 Domain 对象。

例如：

```text
Character → Character
Character → Location
Character → Faction
Event → Location
Story → Character
```

关系必须具有：

```text
source
target
type
state
time_range
metadata
```

例如：

```text
林凡
  --enemy-->
王家
```

关系也可以发生变化。

---

# 11. Timeline

Timeline 是 Core Domain，而不是简单 UI 时间线。

至少需要支持：

```text
World Time
Event Time
Story Time
Scene Time
Character Experience Time
```

时间必须能够参与 Context 和 Validation。

例如：

```text
当前 Scene 时间：
381-03-12 18:30

事件：
黑石城大火
381-03-10
```

系统可以据此判断：

```text
角色是否已经经历该事件？
角色是否可能知道该事件？
某人物此时是否已经死亡？
```

---

# 12. Knowledge

Character Knowledge 是核心能力。

至少区分：

```text
Known
Unknown
Suspected
False Belief
```

例如：

```text
林凡

Known:
王家正在追杀自己

Unknown:
王家真正目的

Suspected:
苏晚晴与王家有关

False Belief:
城主已经死亡
```

Knowledge 必须具有时间维度。

因为：

> 角色现在知道什么，不代表角色过去知道什么。

---

# 13. Constraint

Constraint 表示世界必须遵守的规则。

分级：

```text
System
World
Story
Character
Scene
```

例如：

```text
World:
死人不能复活

Story:
第三卷结束前不能揭露幕后 Boss

Character:
林凡不会主动杀无辜者

Scene:
当前场景必须发生在黑石城
```

Constraint 不只是提示词。

它必须能够参与：

```text
Generation
Validation
Proposal
Commit
```

---

```text
Project
 └── Volume
      └── Arc
           └── Chapter
```

扩展对象：


# 15. Scene 是写作的基本单元

Chapter 是组织结构。

Scene 是真正的创作执行单元。

Scene 至少包含：

```text
scene_id
chapter_id
time
location
characters
purpose
story_threads
content
state
```

未来 AI Generation 优先以 Scene 为上下文边界。

但内部架构不得把正文永久绑定为单纯 textarea。

目标模型：

```text
Chapter
 └── Scene
      ├── Paragraph
      ├── Dialogue
      ├── Action
      ├── Narration
      └── ...
```

这样未来可以实现：

```text

```

# 17. Entity Reference

正文中的实体应该可以被识别为内部引用。

例如：

```text
林凡
```

对应：

```text
Character:char_xxx
```

```text
黑石城
```

对应：

```text
Location:loc_xxx
```

UI 可以：

```text
点击实体
    ↓
打开 Inspector
```

这也是 Context 自动构建的重要基础。

# 18. Context Engine

Context 不等于 Prompt。

Context 是一个结构化对象：

```text
Context
├── Entities
├── Relationships
├── Timeline
├── Knowledge
├── Constraints
├── Story State
├── History
└── Selection Reasons
```

Context Engine 负责：

```text
用户当前目标
+
当前 Scene
+
Story State
+
World State
+
Timeline
+
Knowledge
+
Constraints
+
Relevant History
```

生成最终 Context。

---

# 19. Context Selection

Context 必须可解释。

例如：

```text
林凡

Relevance: 0.94

Reasons:
- 当前 Scene 主角
- 当前 Story Thread 参与者
- 当前 Location 相关角色
- 最近 3 个 Scene 出现
```

系统必须尽可能告诉用户：

> 为什么这个 Entity 被加入 Context？

---

# 20. Context Policy

Context 至少支持：

```text
Automatic
Pinned
Excluded
```

最终：

```text
Final Context
=
Automatic
+
Pinned
-
Excluded
```

Pinned：

> 用户明确要求 AI 必须知道。

Excluded：

> 用户明确要求当前任务不要加入。

# 21. Generation

Generation 是任务，不是简单 API 调用。

模型：

```text

```

包含：

```text

target

model
parameters
status
result

```

例如：

```text

Rewrite Selection
Expand Paragraph
Generate Location
Analyze Character
Check Consistency
```

# 22. Proposal

AI 不允许直接修改 Canonical Domain State。

统一流程：

```text
AI
 ↓
Proposal
 ↓
Validation
 ↓
User Review
 ↓
Accept
 ↓
Command
 ↓
Commit
```

Proposal 必须能够展示：

```text
Added
Removed
Modified
```

以及：

```text
Reason
Evidence
Validation
Risk
```

# 23. Command

所有会改变 Domain State 的操作统一抽象为 Command。

例如：

```text
CreateCharacter
UpdateCharacter
MoveCharacter
CreateLocation
CreateRelationship
CreateScene

```

统一：

```text
Command
 ↓
Validate
 ↓
Execute
 ↓
Event
 ↓
Version
```

AI 和用户最终都应该进入同一套 Domain Mutation Pipeline。

# 24. Event

Command 成功后产生 Event。

例如：

```text

CharacterUpdated
CharacterMoved
RelationshipCreated
SceneCreated
ProposalAccepted
```

Event 的意义：

> 记录世界发生过什么。

V1 不要求完整 Event Sourcing。

但 Domain API 必须为未来 Event Log 保留接口。

# 50. CodeAgent 开发原则

CodeAgent 不应该一次性生成整个项目。

必须遵循：

```text
Analyze
 ↓
Plan
 ↓
Implement
 ↓
Compile
 ↓
Test
 ↓
Inspect
 ↓
Fix
```

每次修改前：

> 优先读取当前真实代码。

不要依赖上一轮 Agent 自己声称：

```text
“我已经修改了 xxx”
```

因为文件才是当前真实状态。

---

# 51. CodeAgent 修改原则

每次修改：

```text
1. 找到真实实现
2. 理解调用链
3. 最小范围修改
4. 保持现有架构
5. 编译
6. 测试
7. 检查副作用
```

禁止为了完成局部功能：

```text
重构整个项目
重新设计已有架构
随意新增依赖
绕过 Domain Layer
复制业务逻辑
```

> **AI 在一个结构化、可验证、可追踪的小说世界中帮助我创作。**

因此最重要的资产不是：

```text
Prompt
```

而是：

```text
World State
Story State
Timeline
Knowledge
Constraint
Context
History
```

AI 是运行在这些数据之上的能力层。

# 57. 开发完成的判断标准

Novel Engine V1 不以“页面做完”为完成标准。

而以这条链路真正跑通为完成标准：

```text
创建 Project
    ↓
创建 World
    ↓
创建 Character / Location / Faction
    ↓
建立 Relationship
    ↓
建立 Timeline
    ↓
创建 Volume / Arc / Chapter / Scene
    ↓
进入 Editor
    ↓
Context Engine 自动构建 Context
    ↓
用户 Pin / Exclude Context
    ↓
执行 AI Generation
    ↓
生成 Proposal
    ↓
Validation
    ↓
用户 Review
    ↓
Accept
    ↓
Command
    ↓
Commit
    ↓
Event
    ↓
Version
    ↓
History 可查看
```

如果这一条链路完整、稳定、可追踪，那么 Novel Engine V1 就已经成立。

否则，即使有：

```text
Graph
漂亮 UI
几十个 AI 功能
几十个设置页面
```

也不算真正完成。

# 58. 一句话架构原则

> **World 是事实，Story 是结构，Timeline 是时间，Knowledge 是认知，Constraint 是规则，Context 是 AI 看到的世界，Generation 是 AI 的推演，Proposal 是 AI 的建议，Validation 是系统的审查，Command 是状态变化的入口，Event 是变化的记录，Version 是对象历史，Snapshot 是世界快照。**

而：

> **Vue 是这个世界的工作台，Rust 是这个世界的运行引擎。**

这就是 Novel Engine 的最终技术定位。
