有，而且我觉得**现在正好是补充这些东西的时候**。你前面的核心架构已经比较完整了，但如果目标真的是做一个以后可以长期使用、甚至让别人也能拿来生成小说的通用框架，我会再补 **8 个关键设计**。

其中有几个甚至比数据库表本身更重要。

---

# 1. 增加「时间线系统」

这是我认为目前最需要补的。

现在我们有：

```text
World
Entity
Event
State
Narrative
Scene
```

但还缺一个统一的：

> **Timeline**

因为长篇小说最容易崩的其实就是时间。

例如：

```text
第10章：
林凡认识苏青

第20章：
林凡认识苏青

第30章：
林凡第一次见苏青
```

这种错误不是 Context 能完全解决的。

---

## 建议

所有重要 Event 都拥有：

```text
event_time
duration
timeline_id
```

并且 Scene 也有：

```text
scene_start_time
scene_end_time
```

形成：

```text
Timeline
│
├── Event
├── Event
├── Scene
├── Event
├── Scene
└── Event
```

以后 Validator 可以直接问：

> 这个 Scene 在时间线上是否合理？

---

# 2. 增加「因果链」

这个非常重要。

现在我们有 Event：

```text
王家袭击矿区
```

但还应该知道：

```text
为什么发生？
导致了什么？
```

所以增加：

```text
CausalRelation
```

例如：

```text
王家资金不足
      ↓
扩大黑铁矿开采
      ↓
发现地下遗迹
      ↓
派人进入遗迹
      ↓
触发封印
      ↓
魔物苏醒
      ↓
黑石城遭袭
```

这样 AI 不只是知道：

> “发生过什么。”

而是知道：

> **“为什么会发生。”**

这会极大提升长篇剧情的一致性。

---

# 3. 增加「剧情线 / Storyline」

你现在有：

```text
Volume
Arc
Sequence
Chapter
Scene
```

但还缺：

> **跨越多个 Arc 的长期剧情线。**

比如：

```text
主角成长线
王家线
地下遗迹线
幕后黑手线
感情线
宗门线
```

它们可能横跨几十卷。

所以建议：

```text
Storyline
```

例如：

```text
Storyline:
    地下遗迹真相

出现：
    Volume 1
    Volume 2
    Volume 4
    Volume 7

最终解决：
    Volume 8
```

这样以后你生成 Volume 5 时，系统知道：

> “地下遗迹这条线还没有解决。”

---

# 4. 增加「伏笔系统」

不要把伏笔仅仅当成 Prompt。

应该是一个正式对象：

```text
Foreshadowing
```

包含：

```text
id
storyline_id
introduced_at
expected_reveal_at
actual_reveal_at
status
importance
hint_level
```

状态：

```text
PLANNED
INTRODUCED
ACTIVE
REVEALED
ABANDONED
```

例如：

```text
地下遗迹存在

第5章：
出现奇怪石碑

第20章：
有人提到古代战争

第50章：
发现地下入口

第100章：
真相揭露
```

系统可以提醒：

> 这个伏笔已经 60 章没有推进。

这对长篇网文非常有价值。

---

# 5. 增加「读者认知状态」

前面我们已经设计了 Character Knowledge。

我建议再正式加入：

```text
ReaderKnowledge
```

因为：

```text
World Truth
Character Knowledge
Reader Knowledge
```

其实是三个完全不同的东西。

例如：

```text
世界真相：
幕后黑手是 A

主角：
不知道

读者：
怀疑 B

反派：
知道 A
```

这就允许系统控制：

```text
悬念
反转
信息差
误导
揭秘
```

---

# 6. 增加「Canon / 非 Canon」

这是做通用小说工具非常值得加入的。

因为 AI 会不断生成：

```text
候选人物
候选地点
废弃剧情
Alternate Plot
```

不能全部直接进入世界。

建议每个生成对象拥有：

```text
status
```

例如：

```text
DRAFT
PROPOSED
CANON
ARCHIVED
REJECTED
```

只有：

```text
CANON
```

才真正属于世界。

---

## 例如

AI：

> 我建议黑石城有地下赌场。

系统先保存：

```text
Location:
地下赌场

status:
PROPOSED
```

你确认以后：

```text
CANON
```

才进入正式世界。

这会让 AI 创作过程非常安全。

---

# 7. 增加「版本 / 分支」

这个是我非常推荐的。

以后你一定会出现：

> “我觉得第 20 章这里写错了，如果把这里改掉，后面怎么办？”

所以最好从设计上支持：

```text
World Version
Narrative Version
```

或者更简单：

```text
Branch
```

例如：

```text
main
 ├── chapter-20-original
 └── chapter-20-rewrite
```

你可以：

```text
方案 A
主角杀死王家家主

方案 B
主角放过王家家主
```

分别继续生成。

最后选择：

```text
B → Merge to Canon
```

---

# 8. 增加「AI 不能知道什么」的机制

这个其实是你整个系统里**非常非常重要的一项**。

我们之前设计了：

```text
Knowledge
```

但还需要：

```text
Visibility
```

例如：

```text
Fact:
幕后黑手是 A
```

可以定义：

```text
Author:
VISIBLE

Narrative Planner:
VISIBLE

Scene Writer:
HIDDEN

主角:
HIDDEN

读者:
HIDDEN
```

甚至：

```text
Scene Writer：
只允许看到“这个事实存在”，
不能看到具体内容。
```

这样你才能真正实现：

> **AI 不是作者上帝视角。**

---

# 9. 再增加一个「Narrative Contract」

这个我很推荐。

每个 Scene 都应该有一个类似：

```text
SceneContract
```

例如：

```text
Scene Objective:
让主角进入黑市

Required:
- 主角进入黑市
- 遇到老板
- 获得一条情报

Forbidden:
- 不得发现地下遗迹
- 不得击杀王家人物
- 不得突破境界

Information:
Reader learns:
- 黑市存在王家眼线

Protagonist learns:
- 王家正在调查自己

World Changes:
- 主角获得黑市通行资格
```

然后 Writer 写完之后：

```text
Draft
 ↓
Contract Validator
```

逐项检查。

这比让另一个 AI：

> “看看这一章写得好不好。”

靠谱得多。

---

# 10. 增加「质量评分」，但不要让它成为唯一判断

可以做：

```text
Continuity Score
Character Score
Plot Score
Knowledge Score
World Score
Style Score
```

例如：

```text
连续性：96
人物一致性：91
剧情目标：100
知识边界：100
世界规则：97
语言风格：87
```

但：

**不要让评分直接决定“好不好”。**

评分的主要用途是：

> 帮你发现问题。

---

# 11. 最后我特别建议加入「Human Approval Gate」

因为你的系统最终不是：

> AI 自己写完整本小说。

而应该是：

```text
AI 提案
 ↓
系统检查
 ↓
用户确认
 ↓
Canon
```

特别是在：

```text
世界观
人物
地点
Volume
Arc
重大剧情
```

这些阶段。

可以：

```text
自动生成
      ↓
┌──────────────┐
│ AI Proposal  │
└──────┬───────┘
       ↓
  用户查看
       ↓
  Accept / Edit / Reject
       ↓
      Canon
```

但是到了：

```text
Scene
Beat
Paragraph
```

就可以高度自动化。

# 13. 还有一个非常关键的原则：不要把“设定”和“生成文本”绑定

例如：

```text
location_designer
```

生成的是：

```text
Location Entity
```

而不是：

```text
一段地点介绍文本
```

同样：

```text
character_designer
```

生成：

```text
Character Entity
```

而不是：

```text
一篇人物小传
```

`scene_writer` 才负责：

```text
Entity
 ↓
Narrative Context
 ↓
小说文本
```

这个区分会让你的系统非常稳定。

---

# 14. 我甚至建议以后 UI 也围绕这个模型做

不要设计成：

```text
输入 Prompt
→ AI 输出
```

而是：

```text
                项目
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
      世界       剧情       知识
       │          │          │
   人物地点     卷/Arc     谁知道什么
   势力资源     Scene       信息差
       │          │          │
       └──────────┼──────────┘
                  ▼
               当前 Scene
                  │
                  ▼
             Context Preview
                  │
                  ▼
                AI生成
                  │
                  ▼
             Validation
                  │
                  ▼
              Commit
```

这样以后你甚至可以做一个：

> **“AI 到底为什么这么写？”**

按钮。

点一下就显示：

```text
本次生成使用了：

人物：
林凡
苏青

地点：
黑石城
黑市

事实：
黑市由地下势力控制

人物知识：
林凡不知道地下遗迹

剧情目标：
获得黑市通行资格

禁止：
发现地下遗迹

Scene #124
Volume #1
Arc #3
```

这会非常爽，而且对于调试 AI 极其有用。

## 最后一个我认为非常重要的建议

**现在先别让 CodeAgent 开始写全部代码。**

你现在已经到了一个非常适合“先做架构冻结”的节点。

下一阶段我建议我们连续把这三个东西定下来：

### ① Domain Schema

精确到：

```text
表
字段
类型
主键
外键
索引
约束
JSON 字段
```

### ② Context Engine Specification

精确到：

```text
给什么
不该给什么
怎么检索
怎么排序
怎么压缩
Token 超了怎么办
角色不知道的信息怎么过滤
```

### ③ Skill Contract

精确到：

```text
location_designer
character_designer
arc_designer
scene_planner
scene_writer
validator
```

每个 Skill：

```text
Input
Context Policy
Prompt
Output Schema
Validation
Side Effects
```

**这三份完成后，才是非常适合交给 CodeAgent 开始实现的时候。**

而且我会建议你把“数据库设计”和“Prompt/Skill 设计”彻底分开：**数据库定义世界，Context 定义 AI 能看到的世界，Skill 定义 AI 如何处理看到的世界。**

这三个边界一旦立住，你这个东西就不再是“AI 帮我写小说”，而是真正意义上的**小说世界状态引擎 + 叙事引擎 + AI Runtime**。
