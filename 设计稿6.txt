有。但这次我会把范围收得很窄：**不是继续往系统里塞模块，而是从“这个系统最终能不能真的长期生成一部长篇小说”反推一次。**

我重新看了一遍我们目前形成的整体设计，我认为还有 **7 个值得补上的关键点**。其中前 4 个我认为应该进入 V1，后 3 个可以 V1.5。

---

# 1. 增加「Story Contract」——一卷/一阶段到底要完成什么

我们现在有：

```text
World
    ↓
Volume
    ↓
Arc
    ↓
Chapter
    ↓
Scene
```

但还缺一个东西：

> **这一层故事结束时，必须发生什么？**

例如第一卷：

```text
Volume 1
使命：
    让主角离开故乡

必须完成：
    ✓ 主角获得金手指
    ✓ 第一次遭遇真正的敌人
    ✓ 建立第一个核心关系
    ✓ 离开青石村
```

可以定义：

```text
StoryContract
├── objectives
├── required_events
├── required_revelations
├── required_character_changes
├── required_world_changes
├── forbidden_events
└── exit_conditions
```

这样 Writer 就不会只知道：

> “现在写第 32 章。”

而知道：

> **“我现在距离这一卷的使命还差什么。”**

这个非常重要。

---

# 2. 增加「Narrative Budget」

这个我认为对中文网文尤其重要。

不是只有：

```text
这一卷 30 万字
```

而应该逐层分配：

```text
Volume
  300,000 字

Arc A
  80,000

Arc B
  120,000

Arc C
  100,000
```

再往下：

```text
Arc B
 ↓
Chapter Budget
 ↓
Scene Budget
```

甚至可以有：

```text
Action
Dialogue
Description
Exposition
Internal Monologue
```

的大致比例。

这样系统可以发现：

> “这个 Arc 已经用了 90% 篇幅，但核心目标只完成了 30%。”

然后主动提醒：

```text
PACING_WARNING
```

而不是等写完才发现：

> “妈的，这一卷怎么写不完了。”

---

# 3. 增加「Foreshadowing Registry」

这个我非常建议。

你之前已经有：

```text
Plot
Event
Revelation
```

但是：

> **伏笔本身应该成为一等对象。**

例如：

```text
Foreshadowing #001

名称：
古井

首次出现：
Chapter 12

表现：
黑市老板提到古井

真正含义：
通往地下遗迹

计划回收：
Chapter 87

当前状态：
PLANTED
```

状态：

```text
PLANNED
PLANTED
REINFORCED
READY
PAID_OFF
ABANDONED
```

这样 AI 每次规划章节时可以知道：

> 当前有哪些伏笔应该被推进。

---

# 4. 增加「Narrative Thread」

这个和伏笔不同。

伏笔：

> 一个信息点。

Narrative Thread：

> **一条持续推进的故事线。**

例如：

```text
Thread #001
王家追杀主角

状态：
ACTIVE

目标：
主角摆脱王家追杀

当前阶段：
追踪

参与人物：
林凡
王家家主
王家护卫

最近进展：
王家发现主角行踪

下一步：
王家派出筑基修士
```

一个 Volume 可以同时存在：

```text
Main Thread
├── 主角成长
├── 王家追杀
├── 金手指秘密
├── 师徒关系
└── 地下遗迹
```

这能解决一个非常现实的问题：

> **长篇小说最容易丢的不是设定，而是剧情线。**

---

# 5. 增加「Time Engine」

这是我认为很容易被忽略的。

你现在已经有 Timeline。

但 Timeline ≠ Time Engine。

例如：

```text
第 1 天
主角进入青石城

第 3 天
王家发现主角

第 5 天
追兵抵达

第 7 天
主角离开
```

系统应该能够回答：

> “当前故事时间是什么？”

以及：

```text
主角从 A 地点到 B 地点需要 3 天
```

那么：

```text
Scene A
Day 10
```

之后不能直接写：

```text
Scene B
Day 10
```

如果两地相距三天。

所以 Location 可以拥有：

```text
travel_time
```

或者更高级：

```text
TravelGraph
```

这会成为后面非常重要的**连续性检查器**。

---

# 6. 增加「Narrative Visibility Engine」

这个其实是你整个项目最有特色的地方之一。

因为你之前说了一个非常关键的问题：

> **主角只能看到自己视角中的东西。**

所以我建议不要只是：

```text
visibility = true/false
```

而应该建立：

```text
VisibilityContext
```

例如：

```text
世界真相：
魔族已经入侵

作者知道：
✓

读者知道：
✗

主角知道：
✗

反派知道：
✓

配角 A：
部分知道
```

于是同一个 Event：

```text
魔族入侵
```

可以有不同的 Narrative Representation。

---

## 这样就能实现真正的信息差

例如：

```text
World Truth
     │
     ├── Character Knowledge
     │
     ├── Reader Knowledge
     │
     └── Author Knowledge
```

以后你甚至可以让 Context Engine 自动控制：

> **这个 Agent 到底有没有资格知道这件事情。**

这个我认为应该成为你系统的核心能力之一。

---

# 7. 最后一个：建立「Novel State Snapshot」

这个和 Context Snapshot 不一样。

### Context Snapshot

> 某一次 AI 调用看到的东西。

### Novel State Snapshot

> **整个小说在某个时间点的状态。**

例如：

```text
Novel Snapshot #120

Story Time:
Day 381

World:
战争爆发

Main Character:
元婴初期

Current Location:
天玄城

Active Threads:
12

Unresolved Foreshadows:
27

Known Characters:
84

Known Locations:
31

Current Volume:
Volume 4

Current Arc:
Arc 2
```

这样你就可以：

```text
Snapshot #120
        ↓
Snapshot #121
        ↓
Snapshot #122
```

甚至：

> “回到第 120 个状态。”

# 但我现在最想强调一个设计思想

你这个项目**千万不要把它设计成“AI 写小说工具”**。

它应该是：

> **一个拥有世界状态、角色认知、剧情状态、时间状态和叙事状态的 Story Engine，而 AI 只是这个 Engine 的一种生成器。**

这两种设计最终差距会非常大。

---

## 错误方向

```text
用户
 ↓
Prompt
 ↓
LLM
 ↓
小说
```

稍微复杂一点：

```text
数据库
 ↓
Prompt
 ↓
LLM
```

最后还是：

> AI 根据一堆设定写东西。

---

## 你现在真正应该做的方向

```text
                Story Engine
                     │
       ┌─────────────┼─────────────┐
       │             │             │
     World        Narrative      Character
       │             │             │
       └─────────────┼─────────────┘
                     │
               Current State
                     │
              Context Engine
                     │
              ┌──────┴──────┐
              │             │
           Planning       Writing
              │             │
              └──────┬──────┘
                     ▼
                    LLM
```

**AI 是可替换的。**

以后你甚至可以：

```text
Claude
GPT
Gemini
本地模型
DeepSeek
```

随便替换。

而你的：

```text
World
Story
Character
Timeline
Knowledge
Thread
Foreshadow
State
```

全部属于你自己的 Engine。

# 所以现在我会建议你停止继续设计数据库

这可能是我给你的最重要建议。

我们现在已经到了一个非常适合：

> **“从架构设计 → 第一版实现”**

的节点。

下一步最值得做的不是继续讨论：

> “还有没有第 38 张表？”

而是拿一个**极小的完整闭环**验证架构。

我建议就是我们之前说的：

```text
World
 ↓
Volume
 ↓
Location Designer
 ↓
Location Proposal
 ↓
Validator
 ↓
Commit
 ↓
Context Engine
 ↓
Scene Planner
 ↓
Writer
 ↓
State Extraction
 ↓
Commit
```

甚至第一版可以只支持：

```text
1 个 World
1 个 Volume
3 个 Locations
3 个 Characters
1 条 Plot Thread
2 个 Foreshadows
3 个 Scenes
```

然后让它真正生成一个小故事。

如果这个闭环能跑通，你就会知道我们现在的架构到底是不是正确的。

**如果这个闭环跑不通，再漂亮的 100 张表都没有意义。**

而以你现在这个项目的目标来看，我认为接下来最有价值的工作已经不是“继续头脑风暴”，而是我直接帮你把这套东西整理成一份可以交给 CodeAgent 执行的：

> **《Novel Engine V1 技术设计规范》**

包括**领域模型 → DuckDB 完整 Schema → Rust 模块结构 → API → Command/Query → Job → Generation → Context → Proposal → Validator → Commit → 第一阶段实施顺序**。

这份才是下一步真正可以拿去开工的东西。
