可以。那我们继续，而且这一步我建议**不要再停留在概念层**，直接把 V1 的 Domain Model 定死。

我会把它设计成一套 CodeAgent 可以直接实现的规格。重点不是“数据库有哪些表”，而是：

> **每个对象到底代表什么、它和谁有关、谁可以修改它、什么时候修改、AI 能看到什么。**

---

# 一、先确定 V1 的核心对象

整个系统最终围绕下面 12 个核心概念运行：

```text
Project
  │
  ├── World
  │     │
  │     ├── Entity
  │     │     ├── Character
  │     │     ├── Location
  │     │     ├── Faction
  │     │     ├── Creature
  │     │     ├── Item
  │     │     └── ...
  │     │
  │     ├── Fact
  │     ├── Relation
  │     ├── Event
  │     └── State
  │
  └── Narrative
        │
        ├── Volume
        │     └── Arc
        │           └── Sequence
        │                 └── Chapter
        │                       └── Scene
        │
        └── CharacterArc

Scene
  ↓
Context Engine
  ↓
Context Package
  ↓
Skill
  ↓
LLM
  ↓
Proposed Changes
  ↓
Validation
  ↓
World State
```

这里有一个非常重要的设计：

**Character、Location、Faction 等不要做成完全独立的世界根对象。**

它们本质上都是：

```text
Entity
```

然后使用：

```text
EntityType
```

区分。

---

# 二、Project

## 定义

Project 是一个完整的小说/故事项目。

例如：

```text
《星海纪元》
```

它是整个系统的根。

---

## Project 负责

```text
项目名称
项目语言
项目设定
默认模型
默认写作风格
默认生成参数
```

但是：

**Project 不保存具体剧情状态。**

---

# 三、World

一个 Project 可以拥有多个 World。

例如：

```text
Project
└── World
      ├── Main Timeline
      └── Alternate Timeline
```

不过 V1 默认：

```text
一个 Project
一个主 World
```

即可。

---

# 四、World 是什么？

World 是：

> **客观存在的世界。**

它不关心：

```text
主角什么时候知道
读者什么时候知道
作者什么时候揭示
```

例如：

```text
黑石城地下存在远古遗迹
```

只要这个事实成立：

```text
World = TRUE
```

---

# 五、Entity

这是整个 World Model 的核心。

统一：

```rust
Entity {
    id
    world_id
    entity_type
    name
    summary
    description
    attributes
}
```

---

# 六、EntityType

不要写死：

```rust
enum EntityType {
    Character,
    Location,
    Faction,
    ...
}
```

数据库层最好允许动态创建。

系统默认：

```text
CHARACTER
LOCATION
FACTION
CREATURE
ITEM
CONCEPT
```

以后用户可以自己增加：

```text
COUNTRY
PLANET
STAR_SYSTEM
RELIGION
TECHNOLOGY
BUILDING
VEHICLE
ORGANIZATION
```

这样你的小说框架才真正通用。

---

# 七、Character

Character 是 Entity 的一种。

但是 Character 的复杂信息不要全部放进 Entity。

建议：

```text
Entity
   +
CharacterProfile
   +
CharacterGoal
   +
CharacterTrait
   +
CharacterArc
   +
CharacterState
```

---

# 八、Character Profile

保存：

```text
姓名
年龄
性别
身份
外貌
背景
社会身份
核心性格
价值观
```

这是比较稳定的信息。

例如：

```text
林凡

身份：
边境散修

性格：
谨慎、现实、观察力强

背景：
出生于小镇
```

---

# 九、Character State

这是非常重要的。

例如：

```text
location = 黑石城
health = 80
cultivation = 炼气三层
money = 350
wanted = true
```

这些都属于：

> 当前状态。

不要和 Character Profile 混在一起。

---

# 十、Character Goal

人物至少要有：

```text
Long Term Goal
Current Goal
Immediate Goal
```

例如：

```text
长期：
成为强者

当前：
进入宗门

当前 Scene：
卖掉手里的妖兽材料
```

这样 AI 才不会把所有人物都写成“剧情工具人”。

---

# 十一、Character Trait

Trait 可以分层：

```text
Personality
Behavior
Value
Fear
Preference
Habit
```

例如：

```text
谨慎
├── 不轻易相信陌生人
├── 喜欢提前准备退路
└── 不会主动承担未知风险
```

这些内容可以用于 Writer。

---

# 十二、Location

Location 同样是 Entity。

但 Location 有自己的结构：

```text
Location
├── Identity
├── Geography
├── Appearance
├── Facilities
├── Population
├── Resources
├── Factions
├── Rules
├── Threats
├── History
├── Secrets
└── Connections
```

---

# 十三、Location 最重要的三个东西

我建议你特别关注：

### 1. Resources

```text
资源
矿产
食物
灵气
人口
财富
特殊材料
```

### 2. Rules

```text
晚上禁止出城
禁止携带武器
进入需要身份牌
```

### 3. Narrative Hooks

```text
可以发生什么剧情
```

例如：

```text
黑市
→ 买卖禁药
→ 情报交易
→ 地下入口
→ 王家眼线
```

这样地点才不是“背景板”。

---

# 十四、Faction

势力也是 Entity。

但是建议增加：

```text
FactionProfile
```

包括：

```text
组织目标
领导人
价值观
资源
领地
成员
敌人
盟友
内部矛盾
秘密
行动方式
```

---

# 十五、Entity Relation

所有实体之间的关系统一用 Relation。

例如：

```text
林凡
  ── MEMBER_OF ──→ 青云宗

王家
  ── CONTROLS ──→ 黑石矿

林凡
  ── ENEMY_OF ──→ 王家

黑石城
  ── CONNECTED_TO ──→ 黑石矿区
```

不要为每种关系建独立表。

---

# 十六、Relation 要有时间

这个非常重要。

例如：

```text
林凡
FRIEND_OF
苏青
```

后来：

```text
FRIEND_OF
→ ENEMY_OF
```

不能直接覆盖。

因为历史剧情会需要：

> “他们什么时候还是朋友？”

所以 Relation 应该支持：

```text
valid_from
valid_until
```

---

# 十七、Fact

Fact 是：

> 世界中的客观事实。

例如：

```text
黑石城属于大周帝国。

地下遗迹存在。

王家控制黑石矿。

黑石矿产出黑铁矿。
```

Fact 和 Entity 不一样。

Entity：

> 黑石城。

Fact：

> 黑石城属于大周帝国。

---

# 十八、Fact 是整个 Context Engine 的基础

因为 Context Engine 最终其实就是：

> 找出当前 Scene 最需要的 Facts。

例如：

```text
Scene：
林凡进入黑市
```

系统检索：

```text
黑市属于黑石城
黑市由地下势力控制
黑市禁止官方人员进入
黑市老板认识苏青
林凡目前没有黑市通行证
```

这些才真正构成 Writer Context。

---

# 十九、Event

Event 表示：

> 世界中发生过什么。

例如：

```text
王家袭击黑石矿
```

Event：

```text
time = 100
location = 黑石矿
participants = 王家、矿工
```

---

# 二十、Event 和 State Change 的区别

这是整个系统最容易混淆的地方。

例如：

> 王家攻占黑石矿。

这是：

```text
Event
```

结果：

```text
矿区控制者 = 王家
```

是：

```text
StateChange
```

所以：

```text
Event
 ↓
StateChange
```

---

# 二十一、StateChange

StateChange 是：

> 世界状态变化的最小记录。

例如：

```text
target:
    黑石矿

key:
    controller

old:
    城主府

new:
    王家
```

它是不可变历史。

---

# 二十二、Current State

为了快速查询：

```text
黑石矿.controller
```

不需要每次重新计算全部历史。

所以建立：

```text
EntityCurrentState
```

这是：

> Projection。

不是事实源。

真正的历史仍然是：

```text
StateChange
```

---

# 二十三、Event → StateChange → Projection

标准流程：

```text
发生 Event
     ↓
产生 StateChange
     ↓
写入历史
     ↓
更新 CurrentState
```

---

# 二十四、Narrative

Narrative 是：

> 作者如何讲述这个世界。

World：

```text
世界是什么
```

Narrative：

```text
我要怎么讲这个世界
```

这是两个完全不同的东西。

---

# 二十五、Volume

Volume 是宏观叙事阶段。

每个 Volume 必须拥有：

```text
Mission
Goal
Conflict
Start State
Target State
Theme
Important Characters
Important Locations
Major Events
Secrets
Foreshadowing
Resolution
```

---

# 二十六、Volume Start / End State

我强烈建议保留。

例如：

```text
Volume 1

Start:
主角不知道修炼世界

End:
主角正式踏入修炼体系
```

这样 AI 才知道：

> 这一卷最终要把故事推到哪里。

---

# 二十七、Arc

Arc 是 Volume 内的剧情单元。

例如：

```text
Volume 1
├── 黑石城 Arc
├── 矿区 Arc
└── 地下遗迹 Arc
```

Arc 必须有：

```text
Goal
Conflict
Participants
Start Condition
End Condition
```

---

# 二十八、Sequence

Sequence 是 Arc 中的一段连续事件。

例如：

```text
黑石城 Arc

Sequence 1：
进入黑石城

Sequence 2：
接触黑市

Sequence 3：
王家追查

Sequence 4：
进入地下遗迹
```

---

# 二十九、Chapter

Chapter 主要是：

> 阅读体验上的章节单位。

不要让 Chapter 承担太多世界逻辑。

真正的剧情控制放在：

```text
Arc
Sequence
Scene
```

---

# 三十、Scene

Scene 是：

> **真正执行 AI 生成的最小叙事单元。**

一个 Scene 必须定义：

```text
Objective
Conflict
Characters
Location
Time
Emotional Goal
Information Goal
Required Events
Forbidden Events
Expected Changes
```

---

# 三十一、Scene Objective

回答：

> 这一幕为什么存在？

例如：

```text
让林凡获得进入黑市的资格。
```

---

# 三十二、Scene Conflict

回答：

> 为什么事情不会直接完成？

例如：

```text
黑市老板不相信林凡。
```

---

# 三十三、Information Goal

非常重要。

例如：

```text
让读者知道：
黑市背后有人控制。
```

但是：

```text
不要让林凡知道：
真正的幕后势力。
```

这就是：

> Information Control。

---

# 三十四、Scene Requirement

可以定义：

```text
必须发生：

林凡进入黑市

必须出现：

黑市老板

必须提及：

黑铁矿

禁止：

林凡发现地下遗迹
```

这对于 Writer 非常重要。

---

# 三十五、Scene Expected Changes

定义：

> 这一幕结束以后，世界应该发生什么变化。

例如：

```text
林凡.location = 黑市

林凡.knowledge += 黑市老板身份

王家.relation_to_林凡 = suspicious
```

这让 Validator 可以检查：

> AI 写完以后，剧情有没有真正推进。

---

# 三十六、Knowledge

现在进入整个系统最关键的一层。

Knowledge 不应该是：

```text
Character.description
```

而应该是独立对象。

例如：

```text
Character:
    林凡

Knowledge:
    黑石城有黑市
    王家正在调查他
```

---

# 三十七、Knowledge 有来源

例如：

```text
通过：
观察
别人告诉
亲身经历
阅读
推理
谣言
```

所以可以记录：

```text
source_type
source_id
```

这样未来甚至可以判断：

> 这个人物为什么知道这件事？

---

# 三十八、Revelation

Revelation 是：

> 一个事实从“未知”变成“已知”的事件。

例如：

```text
Fact:
地下遗迹存在
```

经过 Scene：

```text
林凡发现入口
```

产生：

```text
Revelation
```

然后：

```text
林凡 Knowledge += 地下遗迹存在
```

---

# 三十九、这套模型天然支持“悬念”

例如：

```text
World Truth:
幕后黑手是 X

Author:
知道

反派:
知道

配角:
不知道

主角:
不知道

Reader:
不知道
```

到了第 50 章：

```text
主角获得线索
```

第 70 章：

```text
读者猜到
```

第 100 章：

```text
正式揭露
```

这就不是靠 Prompt 硬写，而是系统本身支持。

---

# 四十、Character Arc

Character Arc 单独存在。

例如：

```text
林凡

Start:
胆小谨慎

Mid:
开始主动承担风险

End:
成为真正的领导者
```

Arc 不是：

```text
人物剧情
```

而是：

> 人物状态变化目标。

---

# 四十一、Authorial Intent

这是给 AI 的“作者层指令”。

例如：

```text
这一段：
节奏快

情绪：
压迫

重点：
表现林凡第一次面对真正强敌时的恐惧

不要：
过度解释世界观
```

它不能改变 World Truth。

它只影响：

> **如何讲故事。**

---

# 四十二、Skill

Skill 是：

> 一个可复用的 AI 能力。

例如：

```text
world_analyzer
volume_designer
arc_designer
character_designer
location_designer
faction_designer
plot_designer
scene_planner
beat_planner
scene_writer
continuity_validator
knowledge_extractor
state_change_extractor
```

---

# 四十三、Skill 必须版本化

例如：

```text
location_designer
v1.0
v1.1
v2.0
```

旧小说生成记录必须知道：

> 当时使用的是哪个 Skill。

否则以后你修改 Prompt，就无法复现旧结果。

---

# 四十四、Generation Run

每一次 AI 调用都应该记录：

```text
Task
Skill
Skill Version
Model
Provider
Context Snapshot
Input
Output
Duration
Status
```

于是你未来可以看到：

```text
为什么这一章写成这样？

因为：

Skill v1.3
Model Qwen
Context Snapshot #9281
```

这对调试极其重要。

---

# 四十五、Context Snapshot

这个对象特别重要。

每次真正调用 LLM：

```text
Context Engine
```

生成一个：

```text
ContextSnapshot
```

然后永久保存。

里面记录：

```text
Scene
World facts
Entities
Relations
Knowledge
Timeline
Requirements
Author Intent
```

这样以后你可以准确复现：

> 当时 AI 到底看到了什么。

---

# 四十六、Context Engine 不应该只是 SQL 查询

建议独立成为一个真正的 Domain Service：

```rust
trait ContextEngine {
    fn build(request: ContextRequest)
        -> ContextPackage;
}
```

它负责：

```text
Retrieval
Ranking
Filtering
Budgeting
Compression
Assembly
```

---

# 四十七、Context Engine 的决策流程

例如当前 Scene：

```text
林凡进入黑市
```

第一步：

```text
Scene Explicit Entities
```

得到：

```text
林凡
黑市
黑市老板
```

第二步：

```text
Current State
```

第三步：

```text
Relations
```

第四步：

```text
Recent Events
```

第五步：

```text
Knowledge
```

第六步：

```text
Narrative Context
```

第七步：

```text
World Rules
```

最后：

```text
Token Budget
```

超出就压缩。

---

# 四十八、Context Ranking

每个 Context Item 可以有：

```text
relevance
importance
recency
explicitness
knowledge_visibility
```

最终计算：

```text
score =
    relevance
  × importance
  × visibility
  × recency
```

然后按照分数选取。

V1 不需要搞复杂机器学习。

规则评分就足够。

---

# 四十九、最重要的 Context Policy

不同 Skill 使用不同 Context。

例如：

### Location Designer

需要：

```text
World
Volume
Arc
Narrative Goals
Existing Locations
Nearby Locations
Resources
Factions
```

不需要：

```text
当前正文
角色私密知识
未来章节
```

---

### Character Designer

需要：

```text
World
Volume
Arc
Faction
Location
Existing Characters
Plot Requirements
```

---

### Scene Writer

需要：

```text
Scene
Characters
Location
Current State
Recent Events
POV Knowledge
Requirements
Author Intent
```

---

### Continuity Validator

需要：

```text
World Truth
Timeline
State History
Scene
Draft
```

---

# 五十、所以最终不是一个 Prompt

而是：

```text
Skill
+
Input Schema
+
Context Policy
+
Output Schema
+
Validator
```

这才是你真正应该设计的 Skill。

```

# 五十三、Runtime 层才知道 LLM

例如：

```

这样以后你换：

不会污染数据库和业务层。

# 五十七、这时候你的“分卷”问题就彻底解决了

你之前担心：

> 主角只能看到当前阶段。

这是对的。

但现在：

```text
World Truth
```

始终存在。

而：

```text
Character Knowledge
```

决定角色知道什么。

而：

```text
Context Policy
```

决定 AI 能看到什么。

于是：

```text
作者视角
角色视角
读者视角
AI Writer 视角
```

可以完全分离。

这是我认为这套系统最重要的设计成果。
