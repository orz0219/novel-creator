可以。下面这份我按**直接交给 CodeAgent 执行**的方式整理，不只是“换数据库”，而是把迁移边界、架构、并发、Repository、迁移策略和验收标准都写进去。

# 小说 Engine 持久层从 DuckDB 迁移至 PostgreSQL 实施设计文档

## 1. 目标

当前项目使用 DuckDB 作为小说 Engine 的持久层。

随着项目逐渐加入多 Agent、CodeAgent、跨会话记忆、Debug 多进程运行等能力，DuckDB 文件锁和多进程访问限制已经开始影响开发稳定性。

本次改造的核心目标：

1. 将主持久层从 DuckDB 迁移至 PostgreSQL。
2. 彻底消除业务层对 DuckDB 文件连接模型的依赖。
3. 建立 Repository / Service 数据访问边界。
4. 使用 PostgreSQL Connection Pool 管理数据库连接。
5. 正确处理并发读写、事务和锁。
6. 为未来的 Agent、跨会话记忆、事件记录和 pgvector 留出扩展空间。
7. 尽可能保证现有业务功能和数据模型不变。
8. 将数据库实现与业务逻辑解耦，避免未来再次进行大规模数据库迁移。

---

# 2. 核心架构调整

## 2.1 旧架构

当前架构类似：

```text
Frontend
   │
   ▼
Rust Backend
   │
   ▼
DuckDB
   │
   ▼
novel.duckdb
```

问题在于 DuckDB 是文件型数据库。

当多个进程同时访问：

```text
Rust Backend
CodeAgent
测试程序
Debug 实例
其他工具
```

并尝试写入同一个 `.duckdb` 文件时，容易产生文件锁、连接冲突和互锁问题。

# 3. 新架构

改造后的目标架构：

```text
                    ┌──────────────────┐
                    │    Vue Frontend  │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │   Rust Backend   │
                    │      Axum        │
                    └────────┬─────────┘
                             │
                  ┌──────────▼──────────┐
                  │      Service        │
                  │      Layer          │
                  └──────────┬──────────┘
                             │
                  ┌──────────▼──────────┐
                  │    Repository       │
                  │       Layer         │
                  └──────────┬──────────┘
                             │
                  ┌──────────▼──────────┐
                  │   PostgreSQL Pool   │
                  └──────────┬──────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │    PostgreSQL    │
                    └──────────────────┘
```

核心原则：

> Agent、Frontend 和业务逻辑都不能直接操作 PostgreSQL。

所有数据库操作统一经过：

```text

 ↓

 ↓
Repository
 ↓

```

# 4. PostgreSQL 选型

数据库统一采用 PostgreSQL。

开发环境推荐使用 Docker：

```text
Rust Backend
     │
     │ TCP
     ▼
PostgreSQL Container
```

例如：

```bash
docker compose up -d postgres
```

不要求生产环境必须使用 Docker。

Docker 主要用于解决开发环境中：

* 数据库生命周期
* Debug 重启
* 环境一致性
* 多进程访问
* 数据库初始化

# 5. Rust 数据库访问层

Rust 后端统一使用 PostgreSQL Connection Pool。

推荐：

```text
SQLx + Tokio + PostgreSQL
```

数据库连接池由 Backend 生命周期统一管理。

例如：

```text
AppState
 ├── db: PgPool
 ├── services
 └── other shared state
```

禁止在业务函数内部反复创建数据库连接。

错误方式：

```rust
fn create_character() {
    let connection = connect_database();
    // ...
}
```

正确方式：

```rust
struct AppState {
    db: PgPool,
}
```

业务代码通过共享 `PgPool` 获取连接。

---

# 17. 事务要求

涉及多个数据库操作的业务逻辑必须使用 Transaction。

例如创建一个完整章节：

```text
BEGIN

INSERT chapter

UPDATE volume

INSERT event

INSERT memory

COMMIT
```

如果任意一步失败：

```text
ROLLBACK
```

不能出现：

```text
chapter 创建成功
volume 更新成功
memory 写入失败
```

导致数据库处于半完成状态。

---

# 18. 并发更新

对于可能被多个 Agent 同时修改的数据，不允许简单地：

```text
SELECT
↓
修改
↓
UPDATE
```

而没有并发控制。

优先考虑 Optimistic Lock。

例如：

```text
version
```

字段：

```text
id
content
version
updated_at
```

更新：

```sql
UPDATE chapters
SET
    content = $1,
    version = version + 1,
    updated_at = NOW()
WHERE id = $2
  AND version = $3;
```

如果影响行数为：

```text
0
```

说明数据已经被其他进程修改。

此时由 Service 层决定：

```text
retry
或者
提示冲突
```

不要静默覆盖其他 Agent 的修改。

数据库连接只需要：


每个进程独立建立 PostgreSQL connection。

PostgreSQL 负责：

* Connection

* Lock

* Deadlock Detection

应用层负责：

* 业务冲突
* Retry
* Optimistic Lock
* Transaction Boundary
